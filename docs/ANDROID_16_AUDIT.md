# Android capture and execution audit

Audited 2026-11-14 against the Android Developers documentation. The application targets API 36 and supports API 31+ on ARM64.

- [Media projection](https://developer.android.com/media/grow/media-projection): each new session uses a fresh consent result. The service is started from a visible activity after consent and enters the `mediaProjection` foreground type before `getMediaProjection`. The token is never persisted or reused. One virtual display is created per session. `onCapturedContentResize` replaces the ImageReader surface and resizes that same display. Register the callback before creating the display. `onStop` releases resources and removes the overlay. The service is `START_NOT_STICKY` and cannot silently restart projection.
- [Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types): the manifest declares the type-specific permissions. Capture has a persistent Stop notification; notification denial does not imply capture consent. Model transfer uses WorkManager with `dataSync`. Explicit offline conversions use a foreground worker with `specialUse` and a subtype declaration. A Play Store release would require reviewing the special-use declaration and store policies.
- [Background foreground-service starts](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start): capture starts only from the foreground activity. An overlay is not used to manufacture capture authorization. On Android 15+, the overlay exemption for starting a foreground service requires a visible overlay; this app does not rely on that exemption for projection startup.
- [Android 16 job changes](https://developer.android.com/about/versions/16/behavior-changes-all): long-running WorkManager jobs can consume job quota even while they run a foreground service. Queued jobs may be delayed by the OS. This build makes the queued state visible and does not promise indefinite, quota-free background computation. Very long conversions require target-device testing; a dedicated user-started inference service is a future option.
- [Application overlays](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY): request `SYSTEM_ALERT_WINDOW` through Settings. Use a small, nonfocusable, nonmodal application-overlay window. Never request accessibility access. Apps can hide overlays on sensitive surfaces; secure content cannot be captured. Overlay-driven activity launches still depend on Android/OEM policy; the foreground notification provides an alternative entry point.
- [Quick Settings tiles](https://developer.android.com/develop/ui/views/quicksettings-tiles): the tile opens the activity and consent workflow, with the PendingIntent overload on API 34+. It never silently starts a new projection. There is no capture boot receiver or background consent flow. WorkManager contributes its own boot receiver and `RECEIVE_BOOT_COMPLETED` permission to reschedule existing jobs; it never restores projection consent.
- Android 15 QPR1+ supplies a prominent projection status chip and can stop projection when the screen locks. Treat all system termination as final; ask for consent again on restart. A selected-app session continues to capture the user's selected app rather than the editor activity.

## Capture correctness boundaries

The overlay is hidden, then a 300 ms compositor settling interval precedes copying the most recent retained ImageReader frame. This is a standard best-effort strategy, not a compositor fence guarantee. It needs visual verification on the Moto tablet, especially with selected-app sharing and slow frames. The original saved image is always visible for review. The capture thread holds at most one image; the reader permits three so a retained image does not stall incoming frames.

No Android target is attached to this workspace. Consent, Nebo overlays, stylus handling, lock/revoke callbacks, OEM background policy and tablet rotations have not been exercised on hardware. Do not represent this audit as device certification.
